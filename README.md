# PawPal+ | AI Pet-Care Assistant

PawPal+ is a Python and Streamlit pet-care scheduling application extended with a retrieval-augmented pet-care assistant. It brings everyday scheduling and sourced general pet-care information together while making clear when an answer is retrieved text rather than model-generated content.

## Project Summary

This project extends my original **PawPal+ pet-care scheduling**. Before the AI extension, the project represented owners, pets, and care tasks, then supported recurring tasks, schedule sorting, task filtering, and conflict detection. The Streamlit interface lets an owner manage pets and tasks and view tasks due today; the CLI demo shows scheduling, recurring tasks, conflicts, and filters.

## Architecture Overview

The Streamlit app in `app.py` connects the existing PawPal+ scheduling domain in `pawpal_system.py` with the pet-care assistant. The scheduling flow continues to manage owners, pets, and tasks and uses `Scheduler.get_todays_schedule()` to show tasks due today in time order.

For a pet-care question, the assistant validates the input, searches the local `knowledge_base/pet_care.json` file using keyword overlap, and checks whether the question is high-risk and whether relevant passages were found. If there is relevant information and the request is in scope, those retrieved passages are included in the prompt sent to the configured local Ollama model. The app displays the response method and the retrieved source names, links, and passages for the user to review.

High-risk questions receive a safety response without model generation. Questions with no relevant passages receive an insufficient-information response. If Ollama is unavailable, or a generated answer fails the safety or context checks, the assistant uses a clearly labeled evidence-only extractive fallback. These flows are shown in [`diagrams/architecture.mmd`](diagrams/architecture.mmd); the tests and evaluation use offline test doubles and do not require Ollama.

The knowledge base is a small curated set of general care passages attributed to the American Veterinary Medical Association (AVMA) and ASPCA Animal Poison Control Center. This is a lightweight keyword-retrieval implementation, not a vector database or a comprehensive veterinary reference library.

## Setup Instructions

1. Clone the repository and enter its folder:

	```bash
	git clone https://github.com/sirigowriupadhye/applied-ai-pawpal-project.git
	cd applied-ai-pawpal-project
	```

2. Create and activate a virtual environment. On Windows PowerShell:

	```powershell
	python -m venv .venv
	.\.venv\Scripts\Activate.ps1
	```

	On macOS or Linux:

	```bash
	python -m venv .venv
	source .venv/bin/activate
	```

3. Install the project dependencies:

	```bash
	python -m pip install -r requirements.txt
	```

4. (Optional) Enable model-generated answers by installing Ollama separately and downloading the default model. Run the Ollama service in its own terminal and leave it running:

	```bash
	ollama pull gemma3:1b
	ollama serve
	```

	Ollama is optional. Without it, the assistant can still retrieve relevant passages and show an evidence-only response; it does not claim that response was generated by a model. Start PawPal+ in another terminal with the virtual environment activated.

5. In a terminal with the virtual environment activated, start PawPal+:

	```bash
	python -m streamlit run app.py
	```

6. Run the automated tests and offline evaluation:

	```bash
	python -m pytest -q
	python evaluate_rag.py
	```

The model defaults to `gemma3:1b` at `http://localhost:11434/api/generate`. Set `PAWPAL_OLLAMA_MODEL` to choose another locally available Ollama model or `PAWPAL_OLLAMA_URL` to use a different local endpoint. The project does not require an API key.

## Pet-Care Assistant and Safety

The assistant provides general educational information, not diagnoses or treatment instructions. It redirects high-risk health questions toward a veterinarian and declines to answer confidently when retrieval finds no relevant passage. The small curated knowledge base is not a substitute for professional veterinary advice.

## Design Decisions

- **Why RAG:** The assistant needs to answer from a small set of inspectable pet-care references instead of relying only on a model's general knowledge. Retrieving first also lets the app show users the sources behind an answer.
- **Knowledge and retrieval:** The curated JSON knowledge base stores passages, source names, URLs, and keywords. A dependency-free keyword-overlap retriever ranks the passages; this keeps the project easy to run and test but is less flexible than semantic or vector search.
- **Generation and evidence use:** When configured Ollama is available, retrieved passage text and the user's question are sent together to the model. A lightweight lexical overlap and unsafe-output check can reject an answer, but it is not a comprehensive factuality or safety verifier.
- **Availability trade-off:** Local Ollama avoids a paid API and API-key management, but requires users to install Ollama and download a model. When the service is absent, the extractive fallback quotes retrieved passages and is explicitly not presented as AI-generated.
- **Scope and limitations:** The knowledge base is small, questions outside it may receive no answer, and the system is not a veterinary professional. The app has no autonomous agent or fine-tuned model. Scheduling sorts by due date and time; although the UI shows duration and priority inputs, the current `Task` model does not store or use those values.

## Implementation Summary

PawPal+ keeps its four core classes in `pawpal_system.py`: Task, Pet, Owner and Scheduler. The application architecture, including the RAG assistant, is in `diagrams/architecture.mmd`.

A Task represents one care activity. It stores a description, a time in 24-hour "HH:MM" format, a frequency ("once", "daily" or "weekly"), a completed flag, and a due date that defaults to today. It can mark itself complete, and its next_occurrence() method returns a new, incomplete copy due one day later for daily tasks or seven days later for weekly tasks. Tasks with any other frequency return nothing.

A Pet stores its name, species, age and its own list of tasks, and it can add a task, remove a task, or return its tasks. An Owner stores a name and a list of pets. It can add or remove pets, and its get_all_tasks() method collects the tasks from every pet into one list.

The Scheduler is connected to a single Owner and reaches tasks through Owner.get_all_tasks(). It sorts tasks by due date and time, filters by pet and completion status, detects exact date-and-time conflicts, and creates the next occurrence of completed daily or weekly tasks. `get_todays_schedule()` returns tasks due today in time order; it accepts an optional date for deterministic use and retains completed tasks so they can be shown in the schedule.

The Streamlit app (`app.py`) manages pets and tasks, generates today's schedule, and provides the pet-care question assistant. The command-line demo (`main.py`) continues to demonstrate scheduling, filtering, conflicts, and recurring tasks. Tests cover both the existing scheduler and the RAG workflow.

## Formatting Features

## 🎨 CLI Formatting Features

The command-line demo (`main.py`) prints its results as readable, color-coded tables instead of plain text. It uses only Python's standard library, so there is nothing extra to install.

Features:

- Bordered tables: the schedule and every filter result print as aligned tables with the columns Time, Pet, Task, Frequency and Status.
- Pet emojis: 🐕 for dogs, 🐈 for cats and 🐾 for any other species.
- Task emojis: the task description picks the emoji: 🚶 walk, 🍖 feeding or breakfast, 💊 medication, 🎾 play, 🛁 grooming, 🩺 vet, and 📋 for anything else.
- Status indicators: ✅ Done is shown in green and ⏳ To do in yellow.
- Color coding: times are cyan, headings and table headers are bold, conflict warnings are red with a 🚨, and the completed-task message is green.
- Section headings: each part of the demo (schedule, conflict check, filters) has an emoji heading with an underline.

**Functions in `main.py`**

| Function | What it does |
|----------|--------------|
| print_task_table(tasks, pet_for_task) | Builds and prints a bordered table of tasks, with emojis and a colored status. Prints "(no tasks)" if the list is empty. |
| print_heading(title) | Prints a bold section title with an underline. |
| get_pet_emoji(species) | Returns an emoji for the pet's species. |
| get_task_emoji(description) | Returns an emoji by looking for keywords in the task description. |
| colorize(text, code) | Wraps text in an ANSI color code. It does nothing when color is turned off. |
| display_width(text) | Measures how many terminal columns text takes, counting emojis as two, so table columns line up. |
| pad(text, width) | Pads text to a column width using display_width(). |


## Testing Summary

The following checks were run against the current project:

- `python -m pytest -q`: **58 passed, 0 failed**. The suite covers the original pet/task/scheduling behavior, today's schedule filtering and ordering, RAG retrieval and source metadata, context passing to the generator, input validation, insufficient evidence, safety redirects, retrieval errors, and model-error or ungrounded-answer fallbacks. Tests use fakes or mocked service calls; they do not require paid API calls or a running Ollama service.
- `python evaluate_rag.py`: **13/13 checks passed**. Across four supported questions, expected retrieval hit rate was **100% (4/4)**, all retrieved passages had source names and HTTPS links, and mean answer/context token overlap was **90%**. The evaluation also confirmed that an unsupported question returns the no-source response without generation. The overlap uses a 50% minimum for each case as a basic lexical signal; it is not proof of factual correctness.
- The Streamlit app was run and a food-safety question was submitted. The app retrieved and displayed the ASPCA source and the evidence-only fallback. The local Ollama service was unavailable, so live model-generated answers were not verified.

Code review identified that retrieval exceptions were not converted into a user-safe assistant response. The assistant now logs the failure type without logging the question or exception details, skips generation, and returns a clear unavailable-knowledge-base message; regression tests verify this behavior and a missing knowledge-base file error. Testing also confirmed distinct messages for unavailable Ollama and rejected model output. Semantic relevance beyond the four fixed evaluation questions and factual quality of live model output remain unverified.
