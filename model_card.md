# PawPal+ Model Card

## 1. Project and AI System Overview

PawPal+ is my pet-care scheduling application, originally developed as the PawPal+ project for Modules 1–3. Its Python scheduling system represents owners, pets, and care tasks; it supports recurring tasks, date-and-time sorting, filtering, conflict detection, and a daily schedule. The Streamlit interface lets an owner manage pets and tasks and view tasks due today.

I extended PawPal+ with a retrieval-augmented pet-care assistant in the same Streamlit application. When a user asks a question, the assistant validates it, searches a small local JSON knowledge base using keyword overlap, and passes the retrieved passages with the question to a locally configured Ollama model. The answer displays the retrieval sources. If no relevant passage is found, the assistant reports that it cannot answer confidently; if Ollama is unavailable or its output fails the basic safety or context checks, it displays a clearly labeled evidence-only extractive response instead of claiming that the text was generated by AI.

## 2. AI Collaboration

I used GitHub Copilot to help extend my existing PawPal+ application rather than replace it. I asked it to inspect the project, propose an integration approach, and help implement and test the retrieval, answer-generation, safety, and Streamlit interface components. I reviewed the suggestions against the existing code and project requirements, ran the automated tests and offline evaluation, and tried the assistant in the running app. That testing confirmed retrieval, source display, and the fallback behavior; because Ollama was unavailable, I did not treat live model-generated answers as verified. I also checked the architecture diagram against the code and asked for it to be corrected when its flows did not match the implementation.

## 3. Suggestion Accepted

I accepted the proposal to keep the pet-care assistant inside the existing Streamlit app and separate its knowledge retrieval, generation, and answer orchestration into small Python components. I also accepted using a local Ollama model when available and a clearly labeled extractive fallback when it is not. This fit the project’s no-paid-API testing requirement and let the existing pet and scheduling features remain in place. The fallback’s label is important: retrieved text alone should not be presented as AI-generated prose.

## 4. Suggestion Rejected or Revised

I revised the first architecture diagram suggestion after comparing it with the implemented control flow. The initial diagram could be read as sending high-risk questions through Ollama and connecting offline tests directly to a live model. In the code, high-risk questions and questions with no retrieved passages return before generation, and tests use fakes or mocked service calls. I asked for the diagram to be corrected to show those branches and human review of displayed sources. This made the diagram more faithful to the application rather than implying components or behavior that were not implemented.

## 5. System Limitations

- The knowledge base contains only a few general-care passages attributed to the AVMA and ASPCA Animal Poison Control Center. It does not cover every pet species, condition, question, or individual circumstance.
- Retrieval uses keyword overlap rather than semantic search. It may miss relevant passages when a question uses different wording, and matching terms do not guarantee that a retrieved passage fully answers the question.
- The answer check is a lightweight lexical overlap check plus a list of unsafe-output terms. It is not a comprehensive fact-checker or guarantee against inaccurate, incomplete, or misleading model output.
- The model is prompted to use the retrieved context, but prompts cannot guarantee that a language model will follow instructions perfectly. Live model output was not verified in the project environment because the local Ollama service was unavailable during testing.
- The offline evaluation checks four supported questions for expected document retrieval, presence of source names and HTTPS links, and at least 50% lexical overlap between the evidence-only answer and retrieved passage text. It also checks one unsupported question for the no-source response. The latest run passed 13/13 checks, with 4/4 expected documents retrieved and 90% mean answer/context overlap. These are small, hand-selected smoke checks; they do not establish broad retrieval quality or prove factual accuracy.
- The system cannot examine or diagnose an animal, assess an exposure, or provide individualized treatment. Pet-health decisions and urgent concerns require a qualified veterinarian; the knowledge base and assistant are not substitutes for professional care.

## 6. Responsible AI Considerations

The assistant retrieves source-attributed passages before model generation and displays the retrieved source names and links so users can inspect them. It is designed to avoid answering confidently when retrieval returns nothing. High-risk health questions are redirected toward veterinary care, while basic input validation and error handling prevent invalid questions, retrieval failures, or an unavailable model service from being treated as a successful generated answer. Retrieval failures are logged by exception type without including the user's question or exception details.

The fallback is explicitly labeled as evidence-only and not model-generated. This distinction helps users understand what the system did. The context and unsafe-output checks are limited safeguards, not proof that an answer is safe or correct. I would use PawPal+ for general educational information only, verify important claims against the cited source, and consult a veterinarian for advice about an individual pet.
